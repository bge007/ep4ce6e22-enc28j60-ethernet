# ENC28J60 gotchas found on real hardware

Five bugs in this project's ENC28J60 driver were invisible in simulation and
cost days each on the bench. Three are in `rtl/net_stack.v`, two in
`rtl/eth_top.v`'s reset and configuration sequences. None is exotic
— they are the kind of thing a driver written from register summaries rather
than from the datasheet will reliably get wrong — so they are written up here
in the hope of saving someone else the same week.

All three were found by making the *chip* — or the driver — report its own
state, not by reasoning about what the code ought to be doing. That is the
practical lesson: when a frame does not arrive, the useful question is not "is
my code right?" but "what does the part say happened?" The third bug in
particular was invisible until a counter was added that could distinguish a
stuck state machine from an idle one.

---

## 1. Every transmitted frame had a bad CRC

### Symptom

Nothing on the network ever received a frame. `ping` said "Destination host
unreachable" forever. From the far end the failure looked total, and every
obvious explanation was wrong in a way that wasted time:

- the switch port showed `InOctets` climbing — so bits *were* leaving the board
- but `InUcastPkts` stayed at `0` — so nothing counted as a packet
- and every switch error counter (CRC, runts, giants, collisions) read `0`

That combination is confusing until you know that a Cisco 2960 discards a
bad-CRC frame at the port without incrementing a visible error counter on the
path we were watching. The frame is simply gone. Octets in, packets out, no
errors: a silent drop.

### Diagnosis

The ENC28J60 writes a **7-byte transmit status vector** into its own buffer
memory immediately past `ETXND` after every transmission (datasheet §7.1,
Table 7-1). It is readable with the same Read Buffer Memory (`0x3A`) opcode the
receive path already uses. Reading it back is the single highest-value
diagnostic on this part, and this project should have done it on day one.

It said:

```
n=003C  w=003C  s2=90  s3=00
```

- `n=0x3C` — 60 bytes queued, correct
- `w=0x3C` — 60 bytes actually on the wire, so the TX engine ran to completion
- `s2=0x90` — bit 7 **Transmit Done**, and bit 4 **TRANSMIT CRC ERROR**
- `s3=0x00` — no deferrals, no excessive collisions, no giant, no underrun

The part transmitted the full frame, considered itself finished, and appended a
wrong CRC. Everything downstream was behaving correctly by discarding it.

### Fix

Each frame in the transmit buffer is preceded by a **per-packet control byte**
(datasheet Figure 7-1) whose bits can override the global `MACON3` settings for
that frame alone:

| bit | name | meaning when set |
|---|---|---|
| 0 | `POVERRIDE` | honour bits 1–3 instead of `MACON3` |
| 1 | `PCRCEN` | generate and append a CRC |
| 2 | `PPADEN` | pad short frames |
| 3 | `PHUGEEN` | allow oversized frames |

The driver had been writing `0x00` there — meaning "use `MACON3`" — and
`MACON3`'s `TXCRCEN` bit is one this project could never read back to confirm
(see the note on MAC-register reads below). Writing **`0x07`** instead
(`POVERRIDE | PCRCEN | PPADEN`) forces padding and CRC generation per frame and
removes the dependency on a global register whose contents were unverifiable:

```verilog
spi_tx <= (txpos == 6'd0) ? 8'h07 : arp_reply_byte(txpos - 6'd1);
```

The ARP cache resolved on the next test.

### Worth knowing

An unpadded ARP reply is 42 bytes, and Ethernet's minimum frame is 60. Real
switches drop runts silently too, so `PPADEN` matters for the same
no-visible-error reason. Both faults were present at once, which is why fixing
either alone changed nothing.

## 2. Bank selects were switching the receiver off

### Symptom

Far subtler, and it survived the CRC fix. Both nodes would come up, answer ARP
correctly for anywhere between thirty seconds and several minutes, and then
**stop receiving entirely** — console counters frozen, `ping` back to
"unreachable", and the node dead until reset.

The frozen counters were the clue that eventually cracked it. This design's
console only emits a telemetry line when a counter *changes*, so silence means
the receive FSM is not merely mis-parsing packets, it is not seeing any. The
part had stopped handing over frames altogether.

### Diagnosis

`ECON1` is the ENC28J60's most-written register, and it is doing two unrelated
jobs at once:

```
bit  7      6      5      4       3      2      1      0
     TXRST  RXRST  DMAST  CSUMEN  TXRTS  RXEN   BSEL1  BSEL0
```

The bank-select bits live in the same byte as `RXEN`, the master receive
enable. This driver selected a bank with a whole-byte Write Control Register:

```verilog
wcr_addr <= A_ECON1; wcr_data <= 8'h00;    // "select bank 0"
```

`0x00` selects bank 0 — and writes a zero into `RXEN`, switching the receiver
off as a side effect. There were four such sites, on the receive cleanup path,
the transmit path and the message path. The receiver was being switched off and
on constantly, and any frame arriving inside one of those windows was lost.

An earlier attempt to patch this by writing `0x04` (bank 0, `RXEN` preserved)
made behaviour *worse*, which sent the investigation down a blind alley for a
while. The reason is the same bug from the other side: `0x04` also writes a
zero into `TXRTS`, and clearing `TXRTS` mid-transmission aborts the frame in
flight. **A whole-byte write to `ECON1` cannot avoid collateral damage.** There
is no safe value.

### Fix

The datasheet provides exactly the right primitive, and this driver simply had
not implemented it: the **Bit Field Set (`0x80 | addr`)** and **Bit Field Clear
(`0xA0 | addr`)** opcodes take a mask and OR / AND-NOT it into the register,
touching nothing else. They are legal on ETH-type registers, which `ECON1` is.

Every `ECON1` access now goes through them. A bank select became two bit-field
ops — clear `BSEL[1:0]`, then set the wanted bits — and `RXEN` and `TXRTS` are
never disturbed:

```verilog
function [7:0] BFS(input [4:0] a); BFS = {3'b100, a}; endfunction
function [7:0] BFC(input [4:0] a); BFC = {3'b101, a}; endfunction
```

The `TXRST` pulse, `TXRTS`, and the `RXRST` receive resync all moved to
single-bit operations at the same time. The resync additionally now clears
`RXEN` *first*, which is what the datasheet requires before `ERXST`/`ERXND` may
be moved.

### Regression test

This one is reproducible off-hardware once you know to look for it, so the
testbench ENC28J60 models gained `BFS`/`BFC` support and a watchdog: once
`RXEN` has been turned on, it may never go off again except while `RXRST` is
being pulsed. `tb_m3` and `tb_m4` assert it.

The assertion was checked against the *old* RTL to confirm it actually catches
the bug rather than passing vacuously:

```
pre-fix:   FAIL: RXEN was cleared outside an RXRST pulse (bank select clobbered ECON1)
post-fix:  PASS
```

After the fix a node soaked for 25 consecutive ping rounds with zero failures
and steadily advancing counters, where before it had failed every round.

## 3. A two-byte SPI helper that hung when data collided with its opcode

### Symptom

Nodes ran correctly for a minute or two and then froze completely — console
counters stopped, `ping` back to "unreachable", dead until reset. This
survived both fixes above and looked identical to §2 from the outside.

### Diagnosis

The console prints only when a counter changes, so a frozen node and an idle
one are indistinguishable. Two cheap additions separated them:

- a **heartbeat**, so the console reports on a timer rather than on change
- a **poll counter** (`P=`), incremented once per `EPKTCNT` poll, plus the
  value that poll read (`K=`)

The wedge was then unambiguous in one line:

```
319s  F=009C R=0008 E=48 S=01 A=0098 T=0806 X=0000 P=14E4 K=01
```

`P` never changed again — the FSM was genuinely stuck, not starved — and
`K=01` said the part had a packet waiting that was never collected. That
pointed at the receive path, after the poll and before the next poll.

The two-byte SPI helpers (`WCR`, `RCR`, `BFS`/`BFC`, and the `EPKTCNT` poll)
worked out which byte they were sending by comparing the byte just shifted
out against the opcode:

```verilog
if (spi_tx == WCR(wcr_addr)) begin      // "still in phase 1?"
    spi_tx <= wcr_data; ...
```

That is correct right up until the **data byte equals the opcode byte**. Then
the comparison stays true, the helper resends the data, sees a match again,
and spins forever.

`WCR(ERDPTL)` is `0x40` and `WCR(ERXRDPTL)` is `0x4C` — and both are written
with the *low byte of an RX ring pointer*, which walks through all 256 values
as packets march up the buffer. Two chances in 256 per frame, so a mean of
about 128 frames to failure. Observed wedges: **122, 156 and 134 frames.**

### Fix

Track the phase in a register instead of inferring it from the data:

```verilog
S_WCR_DATA:
    if (spi_done) begin
        if (!op_ph2) begin
            op_ph2 <= 1'b1;
            spi_tx <= wcr_data; spi_start <= 1'b1;
```

Applied to all four helpers; there are no value-inferred phase tests left.

### Regression test

`tb_m3` scenario 3 injects a frame whose next-packet pointer is `0x004D`, so
`ERXRDPT` is written as `0x4C` through opcode `0x4C`. There is no assertion
on the hang itself — if the FSM wedges, `frames_seen` never reaches 3 and the
testbench times out. Checked against the pre-fix RTL to confirm it fails
there rather than passing vacuously.

After the fix a node ran **365 frames** against a previous mean of ~137, with
the poll counter advancing throughout.

### Worth knowing

The general lesson is worth more than the specific bug: **never infer control
state from data you do not control.** The same pattern is easy to write for
any two-phase protocol, and it fails rarely enough to look like flaky
hardware. A one-bit register costs nothing.

## 4. Reflashing the FPGA does not reset the ENC28J60

### Symptom

After programming the FPGA over JTAG, a node would come up and never work at
all: frames were counted, but not one was recognised as ARP, nothing was ever
transmitted, and the pointer-chain resync counter climbed into the hundreds.

```
F=014D R=0000 E=00 S=00 A=0000 T=0000 X=0095
```

`F` high with `A` and `R` at zero is the signature: the receive path is walking
bytes, but they are not the bytes it thinks they are. Every frame parsed as
garbage. Power-cycling fixed it; reflashing did not.

### Diagnosis

A JTAG reconfigure restarts the FPGA but leaves the ENC28J60 exactly as it
was — mid-stream, with a buffer full of data and its internal pointers
wherever they happened to be. The driver's own state resets to "empty buffer,
start at `ERXST`". The two disagree, and everything after that is misaligned.

The driver did issue a System Reset command (`0xFF`) at startup, so this looked
like it should have been handled. Errata DS80349C item 19 explains why it was
not:

> When operating in Power Save mode (`ECON2.PWRSV = 1`), issuing the SPI System
> Reset command will have no effect.

The errata gives an explicit sequence "for a device in an unknown state", which
is precisely what a reconfigure leaves behind:

1. Bit Field Clear `ECON2.PWRSV`
2. wait at least 300 µs for the regulator
3. issue the System Reset command
4. wait 1 ms
5. **confirm the reset took** — read `ESTAT`, check `CLKRDY` (bit 0) is set and
   the unimplemented bit 3 is clear; if not, repeat from step 1

This driver did step 3 and a generous version of step 4. It did not clear
`PWRSV` first, and never checked that the reset had happened — so a part that
ignored the reset was configured anyway, and looked identical to a driver bug.

### Fix

The full sequence, retrying from step 1 whenever `CLKRDY` does not confirm.
Step 5 is the part worth keeping even if the others feel like belt and braces:
it converts "silently misconfigured" into "retries until ready".

### Regression test

`tb_m1` asserts `PWRSV` was cleared before the reset, and the ENC28J60 models
in `tb_m1`/`tb_m2` now answer an `ESTAT` read with `CLKRDY` set — without which
the design correctly refuses to proceed, which is how the missing model support
announced itself.

### Worth knowing

This is why "power-cycle it" kept appearing to fix things during the earlier
debugging, and why several conclusions drawn right after a reflash were wrong.
If a peripheral has its own reset domain, reconfiguring the FPGA is not a
system reset, and any measurement taken in that window is suspect.

## 5. One SPI timing violation, four years of symptoms

### Symptom

Board-to-board messaging did not work. Host A transmitted correctly — the
switch counted `+1` unicast and `+67` octets, exactly a 21-byte UDP payload
plus headers and CRC — and forwarded it to Host B's port. Host B received
nothing, while still answering ARP and accepting UDP *broadcasts*. Only unicast
addressed to it vanished.

### Diagnosis

A message counter (`M=` on the console) separated "a frame went past" from "a
message was accepted and stored", which until then only the OLED could show.
With it, one pair of tests was decisive:

```
PC unicast   to 192.168.1.61:1234  ->  M=0000   rejected
PC broadcast to 192.168.1.255:1234 ->  M=0001   accepted
```

A temporary promiscuous build (`ERXFCON = 0x20`, CRC check only, no address
match) accepted the same unicast, which put the fault in the part's own receive
filter. From there it was a matter of elimination:

- `ERXFCON` read back as `0xA1` — `UCEN | CRCEN | BCEN`, exactly as written. It
  is an ETH register, so that read is trustworthy.
- The PC's ARP table held `02-42-ce-60-00-02` for `.61`, and the switch
  forwarded the frame to that port. So the frame really was addressed to us.
- `UCEN` matches incoming frames against `MAADR1..6`.

So `MAADR` had to be wrong. Reading it back required fixing the read protocol
first: MAC and MII registers shift out a **dummy byte** before the data
(datasheet 4.2.1, Figure 4-4), making those reads three bytes where ETH and
common registers take two. That alone explains why this project's earlier
MAC-register readback attempts returned nonsense and were abandoned.

With a correct three-byte read the part reported `MAC=000000004200` against an
expected `0242CE600002`. The MAC address was not in the chip.

The reason is one line of the SPI timing table (Table 16-3), `TCSH`, CS Hold
Time — which is not a single number:

| | minimum |
|---|---|
| ETH registers and memory buffer | **10 ns** |
| MAC and MII registers | **210 ns** |

Twenty-one times longer. This design raised CS one clock after the last SPI
byte — 20 ns at 50 MHz. Comfortably legal for ETH registers, and a gross
violation for MAC and MII ones. So ETH access worked perfectly while **every
MAC and MII register write silently failed to commit**, and every MAC read
returned garbage.

### Fix

Hold CS low for 16 clocks (320 ns) after the last byte of any transaction in
the configuration FSM, then raise it:

```verilog
S_CS_HOLD:
    if (csh_cnt == T_CSH[4:0]) begin
        m12_cs_n <= 1'b1;
        state    <= csh_ret;
    end else begin
        csh_cnt <= csh_cnt + 5'd1;
    end
```

Only that FSM needs it. `net_stack` touches ETH and common registers
exclusively, so the receive and transmit hot paths are untouched and pay
nothing for this.

Immediately afterwards the part reported

```
ID HOST=B BLD=000A MAC=0242CE600002
```

and unicast reception started working:

```
PC unicast          -> M=0001
Host A types a line -> M=0002
Host A types again  -> M=0003
```

### How much this one bug explains

It is worth listing, because the symptoms looked unrelated for a long time:

- **`MAADR` never held the MAC address.** The unicast filter never matched, so
  each node answered broadcast ARP and dropped every unicast frame sent to it.
  Board-to-board messaging could never have worked.
- **`MACON3.TXCRCEN` never took.** That is why transmitted frames had bad CRCs
  (fault 1) and why the per-packet control byte `0x07` was needed to force
  padding and CRC per frame. That workaround is still correct and worth
  keeping — it does not depend on a global register — but the underlying
  reason it was necessary was this.
- **`MABBIPG`, `MAIPGL/H`, `MAMXFL`, `MACON1/4` never took either.** The part
  ran on reset defaults throughout.
- **MAC-register readback "did not work"** and was written off as an
  unexplained quirk of the silicon. It was a timing violation, not silicon.

### Worth knowing

Two lessons, both cheap:

**A register you cannot read back is a register you have not configured, only
assumed.** `MAADR` looked right in the source from day one. Nothing complained,
because the only feature that depends on it is unicast reception — and nothing
exercised that until board-to-board messaging.

**When a datasheet gives one parameter two values, find out which one you
are.** `TCSH` has separate ETH and MAC/MII rows. A driver that reads the first
row and moves on gets a design that works for most of its accesses and fails
silently, and only partially, on the rest.

## A related trap: a bad module looks exactly like a bad driver

While chasing the above, one node was corrupting its receive packet chain —
the 6-byte per-packet header's "next packet pointer" would come back out of
range, and since the entire receive path is threaded through that pointer, one
bad value desynchronises everything after it. The driver carries a guard for
this (`next_ptr_ok`, plus a hard `RXRST` resync and an `rx_resyncs` counter on
the console) and it is worth having regardless.

But the corruption itself turned out to be **a faulty ENC28J60 module**.
Swapping it for another of the same part number took the resync counter from
climbing every few frames to a flat `0000`, with no code change at all.

The trap is that this looked identical to a driver bug for a long time. Two
things separate them, and both are cheap:

- **A counter for the anomaly.** `rx_resyncs` on the console is what made
  "this module corrupts the chain and that one does not" a one-glance
  comparison instead of an argument.
- **A second board.** Any behaviour present on one node and absent on the
  other, running the same bitstream, is hardware until proven otherwise.

Note that swapping the module did *not* fix the wedging in §2 — it removed the
chain corruption and left the frozen-counter fault untouched. Two independent
faults with overlapping symptoms is the normal case on the bench, and it is
worth resisting the urge to attribute everything to one root cause.

## MAC-type register reads

For completeness, since it comes up in the fixes above: this project never got
reads of MAC-type registers (`MACON1`, `MACON3`, …) working. Those registers
return a dummy byte first, so they need a 3-byte transaction where ETH-type
registers need 2. Two different attempts produced wrong values on real silicon,
and the diagnostic was dropped.

This does not affect the writes — M2's `RXEN` readback via `ECON1` (an ETH
register) confirms the write path is sound. It only means `MACON3`'s settings
could not be verified from software, which is precisely why the per-packet
control byte in §1 is the more robust way to guarantee pad and CRC.
